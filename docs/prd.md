## 0. 用户原话（需求第一来源）

> 「其实我主要的场景是针对带 git 的仓库进行会话同步 这样就算是代码变动其实可以用git 进行commit push 在同步 但是会话内容没法同步这个可能要解决 用rsync 或者别的方案 参考 remote 方式配置好机器 无论是向上同步还是向下同步可能都需要」

从这段话里提取出**五个**明确约束，后面所有设计都不得违背：

| # | 约束 | 出处 |
|---|---|---|
| C1 | 对象是**带 git 的仓库**，不是任意目录 | 「针对带 git 的仓库」 |
| C2 | **代码差异不由本产品解决**，交给用户自己的 `git commit` / `git push` | 「代码变动其实可以用git 进行commit push」 |
| C3 | 真正缺的是**会话内容**同步 | 「但是会话内容没法同步这个可能要解决」 |
| C4 | 传输手段**不做限定**（rsync / 别的方案都可以），但机器配置要**参考 remote 方式** | 「用rsync 或者别的方案 参考 remote 方式配置好机器」 |
| C5 | **双向**：上行与下行都要 | 「无论是向上同步还是向下同步可能都需要」 |

**关键推论**：因为 C2，本产品**绝不能**试图去管理或搬运代码。代码与会话是两个
独立的真相来源，各自用自己的通道。这条推论直接决定了下面的「不做」清单。

---

## 1. 问题定义

### 1.1 一句话

**换一台机器，代码能靠 git 跟上，但 AI 会话的对话内容丢了。**

### 1.2 为什么现有方案不合用

已有的会话同步插件（`dsh-session-sync`、`dsh-chatsync`、`dsh-workspace-migrate` 一类）
把整个 harness home 当作一团数据搬运。这带来三个用户已经踩到的问题：

1. **混进了不该同步的东西**：设置、插件、凭据、缓存、别的项目的会话。
2. **和控制代码的 git 形成两套并行的真相**：会话里说「改了 A」，git 里却没有 A。
3. **粒度错位**：用户只想同步「这个仓库的对话」，却被迫接受整机搬运。

本产品的立场：**以仓库为单位绑定，只同步会话。**

## 2. 用户故事

### US-1 换机继续同仓库会话（核心，MVP 必须满足）

> 我在 A 机上对一个仓库做了几小时工作，产生了一串对话。
> 下班回家打开 B 机，`git pull` 拿到代码，然后**想接着那串对话继续**——
> 不是重新问一遍「我们刚才在干嘛」。

**验收要点**：B 机能读到 A 机的完整对话历史，并且**能在这个历史上继续对话**。

### US-2 两端交替使用

> A 机（公司台式）和 B 机（家里笔记本）我都在用同一个仓库。
> 今天在 A 上聊了 3 轮，明天在 B 上聊 2 轮，后天回 A 上接着。
> 我不希望任何一端「覆盖」另一端的历史。

**验收要点**：两端的历史**合并**而不是**覆盖**；增量同步（只传新增，不重传全量）。

### US-3 多机（同一账号 3 台以上）

> 台式、笔记本、还有一台放在机房的机器，都可能轮流用同一个仓库。

**验收要点**：任意两台之间同步后，第三台再同步能拿到全部历史；
不要求同时在线，不需要中心服务器。

### US-4（次要）我换了仓库的克隆位置

> A 机是 `~/my-project`，B 机我习惯放在 `~/work/my-project`。
> 这不应该是两个不同的仓库。

**验收要点**：仓库身份由 **归一化 remote URL** 决定，**不由文件系统路径决定**。

> **分支不参与身份**（重要，详见 §4.4）。同一个仓库在不同分支上产生的会话，
> 归到**同一个绑定**；分支只作为展示层的提示信息。

## 3. 产品原则

| # | 原则 | 说明 |
|---|---|---|
| P1 | **只同步会话，不碰代码** | 代码走用户自己的 git。本产品任何时候都不 commit / push / 修改工作区文件。 |
| P2 | **绝不静默覆盖** | 任何可能丢数据的写入，必须先备份；冲突必须报告给人，由人决定。 |
| P3 | **以仓库为单位，不以机器为单位** | 粒度是「这个仓库的会话」，不是「这台机器的 harness home」。 |
| P4 | **配置不重复** | 机器配置复用用户已有的 SSH 约定（「参考 remote 方式」），不要求重填一遍主机、用户、端口、私钥。 |
| P5 | **对话是私密数据** | 会话内容属于用户的私密数据。同步目标默认应为私有仓库；向公开仓库同步必须经过显式知情确认，且每次上行前重新校验目标可见性。 |

> **P5 补充说明（重要，勿简化）**：这**不是**「公开仓库一律禁止」。
> 硬拦截有三个问题：(1) 只有一个公开仓库的用户产品直接不可用；
> (2) 用户改用 CLI 推送，插件拦不住，反而给人「已保护」的错觉；
> (3) 拦错了位置——风险在「内容被推上去」，不在「启用同步」这个动作。
> 所以采用**默认安全 + 显式知情 + 持续校验**三层，详见 §6。

## 4. MVP 边界（本文最重要的一节）

### 4.1 做（Must Have）

| 编号 | 能力 | 为什么必须在 MVP |
|---|---|---|
| **M1** | **单仓库绑定**：把一个本地仓库路径绑定为一个同步单元 | 没有它，「按仓库同步」这个核心主张不成立 |
| **M2** | **上行**（本机 → 远端） | C5 明文要求 |
| **M3** | **下行**（远端 → 本机），**且下行后会话在 DSH 里可见** | C5 明文要求；「写盘但看不到」等于没做（见 §7.1） |
| **M4** | **冲突提示**：同一会话两端都有新增时，不覆盖，双份保留并报告 | P2；这是唯一会**丢数据**的路径 |
| **M5** | **锚点提示**：记录会话产生时的 commit，pull 后提示「这个会话基于旧 commit」 | 用户原话的隐含诉求：代码走 git 后，会话与代码的对应关系会漂移 |
| **M6** | **仓库可见性闸门**：默认安全 + 显式知情 + 每次上行前重校验 | P5 |
| **M7** | **机器配置复用 SSH 约定**：读 `~/.ssh/config`，不重填连接四要素 | C4 明文要求 |

### 4.2 不做（Out of Scope，附理由）

> 这一节和上面同样重要。**每一条「不做」都是一次有意识的减法**，不是遗漏。

| 编号 | 不做 | 理由 |
|---|---|---|
| **N1** | **搬整个 harness home（`~/.dsh` 全量）** | 用户明确不要，且是现有插件的做法。全量搬运会把设置、插件、凭据、缓存、其它项目的会话一起带走，与 C2「代码走 git」的干净边界冲突。 |
| **N2** | **同步设置与插件** | 这是另一个产品（已有 `dsh-settings-sync` 在做）。混进来会让「同步会话」这件事的认知负担急剧上升，且两者的冲突语义完全不同。 |
| **N3** | **非 git 目录** | C1 明文限定「带 git 的仓库」。非 git 目录没有 remote 身份，无法跨机对齐——强行支持需要引入中心服务器，违背 MVP 的「零基础设施」定位。 |
| **N4** | **附件自动同步** | **实测依据**：本机 218 个会话中，181 个（83%）的文本里出现 `attachment` 字样，但**真正指向附件存储的只有 5 个（2.3%）**——其余绝大多数是 MCP 工具 schema 里的字段名，不是真实引用。为 2.3% 的场景引入二进制对象搬运、内容寻址、去重与 GC，投入产出严重不匹配。**MVP 遇到带附件的会话时，在同步报告里明确点名「该会话含附件，未同步」，绝不静默丢弃。** |
| **N5** | **定时 / 后台自动同步**（MVP 默认关闭） | 自动同步把「我什么时候把对话推到哪里」的决定权从用户手里拿走了，而目标仓库可能是公开的。MVP 要求**用户主动触发**，心智模型清晰。配置项保留（`autoSync` 默认 `false`），但不作为 MVP 验收项。 |
| **N6** | **同一会话的实时协同（两端同时编辑同一会话）** | 这是分布式协同编辑问题，复杂度极高。MVP 只要求「不同时改」的正常路径 + 「同时改了」的检测与报告（M4）。 |
| **N7** | **中心服务器 / 账号体系** | 传输复用用户已有的 git 远端，不引入任何本产品自己的服务端。零运维是 MVP 的强诉求。 |
| **N8** | **会话内容的加密存储** | 方向性要求（见 P5 与 §6.4），但 MVP 先做到「不把明文推到公开仓库」的闸门；端到端加密作为紧随其后的增强，不阻塞 MVP 交付。 |
| **N9** | **子会话（subagent / 委派会话）的独立同步** | **实测依据**：某仓库 35 个会话中 30 个是 subagent 子会话，占 **77% 的字节量**（76.8MB / 99.9MB）。子会话是父会话的中间产物，用户几乎不会直接「读到」它们。MVP **只同步根会话**；子会话不进 MVP（详见 §4.3 的论证与后续风险）。 |

### 4.3 关于 N9（子会话）的额外说明

这是本文里**争议最大**的一条，故单独论证。

**实测数据**（对一个真实仓库 35 个会话做的统计）：

| 类别 | 数量 | 字节数 | 占比 |
|---|---|---|---|
| 根会话（用户直接对话的） | 5 | 23.1 MB | 23% |
| 子会话（subagent 委派产生的） | 30 | 76.8 MB | **77%** |

**为什么不进 MVP**：
- 子会话是**工具的中间过程**，不是用户想「继续」的对话。US-1 ~ US-3 里没有一个故事需要它。
- 体积占 77%，同步它会让 MVP 的传输成本翻 3 倍以上。
- 子会话的正确性依赖父会话的 `subagent/catalog` 目录结构，跨机合并的语义复杂（父会话在一端、子会话在另一端时怎么办？）。

**必须接受的风险（写在这里以免后人有惊喜）**：
> 只同步根会话时，根会话里引用的子会话在 B 机上是缺失的。
> 如果 DSH 的界面会因为缺少子会话而**报错或白屏**，那 N9 就必须撤回。
>
> **待验证（阻塞项，交付前必须给出结论）**：在 B 机上只存在根会话、缺失其子会话时，
> 打开该根会话是否可正常渲染、可继续对话？
> - 若能 → N9 成立，但同步报告里要标注「该会话有 N 个子会话未同步」
> - 若不能 → **N9 撤回**，子会话必须进 MVP（此时需要重新评估体积与冲突策略）

### 4.4 仓库身份不含分支（产品裁决）

**决定：一个仓库 = 一个绑定。`repoKey` 只由归一化 remote URL 构成，分支不参与。**

这曾是实现与设计不一致的地方（ADR-1 说不含分支，`repoKeyOf` 却含），
故在此把产品语义写死，并留下论据。

#### 为什么分支不能进身份

| # | 论据 | 依据 |
|---|---|---|
| **1** | **会话本身没有 branch 属性** | 实测：会话 header 字段为 `cwd / id / createdAt / origin / parentSession / type / version / agentPreset / delegationDepth / isSeeded`，**无 branch、无 commit** |
| **2** | **用分支做键会导致「会话随用户切分支而漂移」** | 同一个会话文件在 T1 属于 `main`、T2 切到 `feature-x` 后属于 `feature-x`——**身份不稳定**，比「跨分支混在一起」严重得多 |
| **3** | **会与发现层自相矛盾** | 会话发现规则是**纯 cwd 匹配**（`sessionBelongsToRepo`），不看分支。绑定层若按分支分键，就会出现「会话在发现集合里、却找不到对应 binding」 |
| **4** | **会推翻 worktree 的设计** | worktree 的定义就是「同一仓库 + 不同分支」（design §3.4 明确说 worktree 共享同一 repoKey）。键里含分支，这条就自相矛盾 |
| **5** | 符合用户心智 | 用户想的是「我那个项目」，不是「我那个项目的 main 分支」 |

#### 「跨分支会话混在一起」不是问题，是正确行为

用户从 `main` 切到 `feature-x`，看到之前在 `main` 上聊的会话——**这是好事**，
他会想起「这个我上周讨论过」。

需要区分时，应在**展示层**（会话列表标注该会话产生时的分支）做，
而不是在**身份层**分键。

> **一句话**：分支属于**展示维度**，不属于**身份维度**。

#### 这条要求带来的两个实现提醒

1. **`repoKeyOf` 需要去掉 `branch`**（当前实现含分支，与 ADR-1 矛盾）。
2. **`branch` 仍要记录**——但只写进 manifest 作为**提示字段**，
   用于展示与锚点过期判断，**不参与身份计算**。

## 5. 用户流程

### 5.1 落点总原则

| 交互 | 落点 | 为什么 |
|---|---|---|
| 首次配置（绑定仓库、确认可见性） | **设置页**（新增「仓库会话同步」分组） | 一次性、需要解释、需要展示风险文案 |
| 日常触发同步 | **设置页按钮** + **Agent 工具**（`repo-session-sync`） | 前者给人用，后者给 Agent 用（Agent 自己知道刚聊完）|
| 冲突处理 | **设置页**的冲突面板 | 需要展示双份内容、需要人做决定 |
| 轻量状态提示 | **设置页**状态行 | MVP 不占用侧栏、不新增常驻入口 |

> **MVP 不做的界面**：不新增侧栏常驻面板、不做浮窗、不做系统通知。
> 理由：这些都会扩大 UI 面积与维护成本，而 MVP 的核心价值（能把会话搬过去）
> 不需要它们。等 M1-M7 跑通后再讨论。

### 5.2 首次配置流程（每台机器一次）

**前置**：本机已装好 DSH，目标仓库已 clone 到本地，`git remote` 已配置。

| 步骤 | 用户动作 | 系统行为 | 失败时 |
|---|---|---|---|
| 1 | 打开 设置 → 「仓库会话同步」 | 显示本机已绑定列表（首次为空）+ 「添加仓库」按钮 | — |
| 2 | 点「添加仓库」，选本地仓库目录 | 校验：目录存在 → 是 git 工作区 → 有 remote。自动读出 remote URL 与当前分支 | 分别提示「路径不存在 / 不是 git 仓库 / 没有配置 remote」（对应 `repo-path-missing` / `not-a-git-repo` / `no-remote`）|
| 3 | 选择**同步方向** | 三选一：**上行**（只推）/ **下行**（只拉）/ **双向**（默认） | — |
| 4 | **系统自动检测仓库可见性** | 判定 `private` / `public` / `unknown`，并展示结果与风险说明 | 判定失败 → 归为 `unknown`，**默认不放行**（见 §6）|
| 5 | 若为 `private` | 直接完成绑定 | — |
| 6 | 若为 `public` **或** `unknown` | 弹风险确认：**必须逐字输入仓库名**（`owner/repo`）才能继续；`public` 额外用红色警示 | 输错 → 提示「输入的和仓库名不一致」；不输 → 无法绑定 |
| 7 | 完成绑定 | 写入绑定表，显示在列表中，状态为「已绑定，未同步」 | — |

**绑定后的机器配置流程（对应 C4「参考 remote 方式配置好机器」）**：

| 情况 | 行为 |
|---|---|
| 用户的 `~/.ssh/config` 里已有这台机器 | **直接复用**。本产品只读该文件，**一行都不写**。 |
| 用户要让插件新建一台 ssh 配置里没有的机器 | 才写入，且严格用「受管块」标记（`# dsh-repo-session-sync: managed`），只动自己标记的块；无标记的同名块一律报冲突、原文一字不改 |
| 绑定表存什么 | **只存 `{id, alias, label}`**，不复制 host / user / port / 私钥。连接事实的唯一真相永远是 `~/.ssh/config` |

> **为什么不复制连接四要素**：一旦插件存了第二份副本，就会与 `~/.ssh/config`
> 不一致，这是经典的两份真相 bug；同时也给了凭据落盘的机会。P4 + P5 都要求不这么做。

### 5.3 日常同步流程（上行）

| 步骤 | 用户动作 | 系统行为 |
|---|---|---|
| 1 | 设置 → 仓库行 → 点「上行」 | 先做**可见性重校验**（见 §6.2） |
| 2 | — | 重校验不通过 → **立即中止**，显示原因（例如「该仓库已变为公开，本次同步已中止」） |
| 3 | — | 扫描该仓库相关的**根会话**，算出每个会话的增量（水位线之后的新事件） |
| 4 | — | 若无可同步内容 → 显示「已是最新」（`up-to-date`） |
| 5 | — | 展示**预览**（将同步 N 个会话 / X KB），用户确认后执行 |
| 6 | 点「确认同步」 | 打包 → 推送到传输通道（MVP 默认：项目仓库的独立 orphan 分支） |
| 7 | — | 显示结果：成功数 / 跳过数 / 字节数 / 失败明细；**含附件被跳过的会话要点名** |

> **MVP 要求「先预览后执行」**：因为上行是「把私密数据推出去」的动作，
> 不可撤销（git 历史可回滚，但内容已离开本机）。这一步不能省。

### 5.4 日常同步流程（下行）

| 步骤 | 用户动作 | 系统行为 |
|---|---|---|
| 1 | 设置 → 仓库行 → 点「下行」 | 拉取远端的会话包 |
| 2 | — | 校验包：格式版本、会话 id 合法性、事件连续性、解码可读性 |
| 3 | — | 对每个会话**逐个分类**：`append`（可接续追加）/ `up-to-date`（已覆盖）/ `gap`（中间缺事件 → 冲突） |
| 4 | — | **写备份快照**（在任何写入之前，备份失败则整次中止） |
| 5 | — | 执行写入：可追加的追加；冲突的**不写**，进入冲突列表 |
| 6 | 用户点「确认」 | 显示结果：新增会话数 / 合并会话数 / 冲突数 / 备份路径 |
| 7 | — | **重启 DSH 后，这些会话在侧栏对应仓库下可见**（见 §7.1 的硬要求） |

### 5.5 冲突了怎么办

**触发条件**：同一会话在两端都有新增事件（远端从 `seq X` 开始，但本机 `nextSeq` 不是 `X`）。

| 步骤 | 用户看到什么 | 可以做什么 |
|---|---|---|
| 1 | 同步结果里出现「N 个会话存在冲突」，红色标记 | — |
| 2 | 点开冲突详情 | 看到：会话标题、本机事件数、远端事件数、**双方分叉的 seq 位置**、各自最后一条消息的时间 |
| 3 | 选择处理方式 | **三选一**：<br>① **保留本机**（远端那份存为旁支副本，不丢）<br>② **采用远端**（本机那份存为旁支副本，不丢）<br>③ **两份都留**（后端各自独立存在，手动决定）|
| 4 | 点确认 | 执行，并在备份目录留下操作前的快照 |

**硬约束**：**绝不静默覆盖**。任何一条路径下，被放弃的那一份都必须先落盘为可恢复的副本。
用户在任何时候都能从备份目录找回。这是 P2，不可协商。

### 5.6 锚点提示流程（M5）

| 时机 | 行为 |
|---|---|
| 上行时 | 记录会话产生时该仓库的 HEAD commit |
| 下行后、且本机 HEAD 与该锚点不同 | 在会话列表上显示提示：「该会话基于 commit `abc1234`，当前 HEAD 是 `def5678`」 |
| 提示的语气 | **信息性，非阻断**。用户可能只是切了分支，或者本来就想在新 commit 上继续。 |

> **为什么锚点只需要「提示」而不需要「阻止」**：因为代码同步走的是用户自己的 git
> （C2），本产品**不知道也不该判断**用户的代码意图。锚点的价值是让人意识到
> 「对话里的上下文可能对应旧代码」，而不是替人做决定。

## 6. 仓库可见性：默认安全 + 显式知情 + 持续校验（M6）

> 这是本 PRD 里唯一涉及**不可逆信息泄露**的设计，措辞与语义都要精确。

### 6.1 三态判定

| 判定 | 含义 | 默认行为 |
|---|---|---|
| `private` | 确认是私有仓库 | **直接放行**，无需确认 |
| `public` | 确认是公开仓库 | **默认阻止**；提供需**逐字输入仓库名**的知情确认逃生口 |
| `unknown` | 无法判定（无 `gh` / 非 GitHub / 无网络 / 无权限） | **默认阻止**，同样需确认 |

**核心原则：`unknown` 不等于安全。** 判定失败绝不静默放行。

### 6.2 两层防御

| 层 | 时机 | 做什么 |
|---|---|---|
| **第一层** | 启用绑定时 | 判定可见性；非 `private` 需要显式知情确认 |
| **第二层** | **每次上行前** | 重新判定；与上次记录的可见性对比，发现安全退化就**中止本次上行** |

**为什么必须有两层**：仓库可能今天私有、明天被改成公开。只在启用时查一次，
等于「装了个只响一次的警报器」。

### 6.3 两种「确认」的语义必须区分（不要合并成一个概念）

这是本 PRD 里最容易被实现方做错的地方，特此单列。

| | **`public` 的确认** | **`unknown` 的确认** |
|---|---|---|
| 触发条件 | 明确知道目标是公开的 | **根本不知道**目标是什么 |
| 确认方式 | **逐字输入 `owner/repo`** | 勾选「我了解风险」即可 |
| 是否长期有效 | **长期有效**，绑定「仓库身份 + 可见性指纹」 | **不长期有效，每次上行都要重新确认** |
| 何时失效 | **可见性一变立即作废** | 天然一次性，无「失效」概念 |
| 记录内容 | `{repoKey, visibility, confirmedAt}`，**不含任何凭据** | **不落盘**（每次重新问） |

**为什么 `public` 要长期有效、而 `unknown` 要每次重问**：
`public` 是**已知的、稳定的**事实，用户明确接受后没必要每次折磨他；
`unknown` 意味着我们**根本不知道**远端状态，没有任何可绑定的指纹，
每次都可能是不同的情况，所以每次都问。

### 6.4 三层机制下的「每次上行前重校验」到底校验什么

> 此处定义必须精确，否则会与「用户确认后可启用」自相矛盾。

**错误做法（会导致死锁）**：每次上行都判「当前是不是 `public`」，是就中止。
→ 用户即使对 `public` 仓库做了知情确认，每次上行仍被中止 → **等价于硬拦截**，
正是 §P5 明确要避免的。

**正确做法**：

> **每次校验的是「可见性有没有偏离用户当初确认的那一种」，不是「是不是 public」。**

| 上次记录的可见性 | 本次判定 | 结果 |
|---|---|---|
| `public`（且用户已逐字确认） | `public` | ✅ **放行**（偏离度为零） |
| `public` | `private` | ✅ 放行（变得**更安全**了，顺带提示可更新记录）|
| `public` | `unknown` | ❌ **中止**（无法确认是否仍为公开）|
| `private` | `public` | ❌ **中止 + 告警**（安全退化，最危险路径）|
| `private` | `unknown` | ❌ **中止**（查不到不等于安全）|
| `unknown` | 任意 | ❌ **中止**，要求重新确认（`unknown` 不绑定 consent）|

**给实现方的明确要求（这是当前代码里的一个真 bug，已知，需修）**：

> 可见性重校验的实现必须把 `previous` 传成**「用户 consent 时记录的可见性」**，
> 而**不是**「上一次运行时的判定结果」。
>
> - 现有 `detectRegression({previous, current})` 在 `prev=public, curr=public` 时
>   返回 `ok:false`（已实测确认）。**这会让用户对 public 仓库确认过之后仍然每次被拦，
>   等价于硬拦截**，正是 P5 要避免的。
> - 正确语义：**consent 有效**且 `curr === consent.visibility` → **放行**。
> - 只有在 `curr !== consent.visibility`（发生偏离）时才中止。

**数据安全要求**：consent 记录只含 `{repoKey, visibility, confirmedAt}`，
**不得包含任何凭据、令牌、私钥内容**。

### 6.5 「我的仓库是公开的怎么办」（用户可见文案要点）

设置页在判定为 `public` 时必须同时给出**两条**可行路径，不能只堵不疏：

1. **推荐路径**：把这个仓库改成私有（给出 GitHub 的设置路径），然后重新检测。
   或：换一个私有仓库用于同步。
2. **知情路径**：如果你确实要推到公开仓库——输入仓库名确认。文案必须写明后果：
   > 「同步会把**完整对话内容**推上去，包括你本机的路径、命令输出、
   > 代码片段，以及你在对话里贴过的任何东西。任何人看到这个仓库就能读到。」

**文案要求**：不得使用「可能」「注意」这类弱化词掩盖后果；必须直说「任何人能读到」。

## 7. 硬性实现要求（PRD 只提要求，不指定实现）

> 以下两条是**产品正确性要求**，不是实现建议。达不到就意味着 MVP 的核心价值没闭环。

### 7.1 下行必须让会话「可见」，而不只是「写盘成功」

**问题**：DSH 的会话列表来自工作区注册表（`workspace.json` 的 `sessionIds`），
**不是扫盘扫出来的**。把会话文件写到 `sessions/` 目录下，用户**在界面里看不到**。

#### 7.1.1 两件事必须同时做，缺一不可见

| # | 必须做 | 为什么 |
|---|---|---|
| **A** | **重写 `cwd`** 为本机的真实仓库路径 | ① 不重写**必然**被 `reportFilteredCandidates()` 剔除（不只是"可能"）<br>② 不重写会让 B 机继续会话时工具在**错误目录**执行——安全风险 |
| **B** | **让 DSH 知道这个会话存在** | 注册表的写入点只在 DSH 自建会话时触发；外部写入的文件不会被自动收养 |

> **只做 A 不做 B，或只做 B 不做 A，用户在界面上都看不到。** 这是两条独立的要求。

#### 7.1.2 关于 B 的优先级（与 `docs/design.md` §11.3 对齐）

| 优先级 | 手段 | 状态 |
|---|---|---|
| **P0** | 通过 DSH 插件的**公开接口**登记到工作区 | **首选**，需 dev-core 确认该接口是否存在 |
| **P1** | 同步完成后给一个入口，**由用户在 DSH 内主动打开一次**，走 DSH 自己的登记路径 | **MVP 可接受的兜底** |
| ❌ | 直接改写 `workspace.json` | **禁止**。那是 DSH 私有状态（带 `version: 2` 与迁移逻辑），抢写权 + 版本风险 + 内存态覆盖 |

#### 7.1.3 🔴 P2「只写文件 + 告知用户」**不被接受为 MVP 交付**

`docs/design.md` §11.3 里列了一个 P2 降级方案（只写文件，UI 上诚实说明
「可能需要重启才能看到」）。**产品侧明确否决这一档作为 MVP 交付**：

- 它意味着 US-1「换机接着聊」**没有闭环**，用户拿到的是一堆打不开的文件。
- 更糟的是：用户看到「同步成功」然后打开侧栏什么都没有——**这比明确报错更糟**，
  用户会以为数据丢了，甚至可能去删除备份。
- 这条链路是本产品**存在的唯一理由**，不能做成半截。

**因此**：P0 与 P1 至少一个必须在 MVP 内成立。
若两者都不可行（DSH 不提供任何登记入口），**这是需要上报的范围问题**，
按「缩小其它功能、保住核心链路」的原则处理，**不得**靠降级 P2 蒙混交付。

#### 7.1.4 目标路径不存在时必须中止

> 下行前检查：重写后的目标仓库路径在 B 机**是否真实存在且是 git 工作区**。
> - 不存在 → **中止本次该会话的下行**，提示「会话需要仓库在 `<path>`，
>   但该路径不存在。请先 clone 该仓库再重试。」
> - 存在但不是同一个仓库（remote 不匹配）→ 中止，提示路径指向了另一个仓库。
> - **绝不**用 A 机的原始路径硬写，**也绝不**用 B 机的"预期路径"硬写。

**为什么这条不能省**：写入一个 `cwd` 指向不存在目录的会话，等于制造一个
「打开就报错」的僵尸会话。而且这种损坏会随着下次上行**扩散回其它机器**——
污染是双向的。

#### 7.1.5 完成判定

> **下行的"完成"判据 = 会话出现在 DSH 的可见集合中**（经 P0 接口确认，
> 或经 DSH 自己的读取路径验证），**不是"文件已落盘"**。

### 7.2 下行必须「先备份再写」

**要求**：任何对本地会话目录的写入，之前必须有一个成功的备份快照。
备份失败 → **整次下行中止**，本地数据一字不动。

**为什么单列**：这是唯一可能**删除/覆盖用户本地数据**的路径。备份不是「尽量做」，
是前置条件。

## 8. 验收标准

> 每条都必须**可测**：给定前置状态，执行动作，断言可观察结果。
> 测试一律使用**隔离的临时 harness home**，绝不触碰用户真实数据。

### AC-1 基本上行 + 下行（核心闭环）

**前置**：A 机与 B 机都已绑定同一仓库（remote 相同），仓库为 `private`。
**动作**：A 机产生 **3 轮**对话 → A 上行 → B 下行。
**断言**：
1. B 机能读到**完整 3 轮**对话（用户消息与助手回复数量与内容均一致）
2. **B 机能在 DSH 界面上打开该会话**（不是只在磁盘上有文件）
3. **B 机能在这个会话上继续对话**，新增内容正常落盘。判定细化：
   - 新事件的 `seq` 从**已同步的最后一个 seq + 1** 开始，连续无缺口
   - 追加后日志仍可正常解码（不产生撕裂帧 / 不可读尾部）
   - 追加后 `header.cwd` **仍是 B 机路径**，没有被同步过程改回 A 机路径
   - `git -C <cwd> rev-parse --show-toplevel` 指向 B 的仓库

> **为什么第 3 条要写这么细**：「能打开」和「能继续」是两回事。
> 若下行的末尾状态（`nextSeq`）不对，DSH 后续追加会失败或产生 seq 冲突。
> **「能打开但不能继续」比「打不开」更糟**——用户会以为同步成功了，
> 干活干到一半才发现会话坏了。

> 第 2 条对应 §7.1。**只满足第 1、3 条不算通过。**
>
> **第 2 条的判定方式必须写清楚**：不能只看「磁盘上有没有文件」，
> 必须在 DSH 界面上确认该会话出现在对应仓库的会话列表中、
> 且**能点开并正常渲染**。仅在文件系统层面验证 = 未验证。
>
> **判定路径按 §7.1.2 的 P0/P1 二选一**：
> - P0（有登记接口）→ 同步完成后**不重启**即可见
> - P1（无登记接口，走用户在 DSH 内主动打开）→ 同步完成后**经该入口**可见
>
> **注意：AC-1 不要求「重启后可见」这一特定实现**——要求的是「用户最终能看到并继续」。
> 若实现选择 P1，测试要验证 P1 入口真实可用，而不是验证重启。

### AC-1b cwd 重写（可见性的前置条件）

**前置**：A 机仓库在路径 `A`，B 机同一仓库克隆在**不同的路径** `B`。
**动作**：A 产生会话 → 上行 → B 下行。
**断言**：
1. B 机上该会话 header 的 `cwd` 已被改写为 `B`（**不是** A 机的路径）
2. B 机在界面上可见并可继续对话（验证 `candidateMatches` 不再过滤它）
3. B 机继续对话时，工具调用落在 `B` 目录下（**不在 A 的路径语义下**）
4. B 机上**不存在**任何指向 A 机路径的会话残留

### AC-1c 目标路径不存在时必须中止

**前置**：B 机**尚未**把仓库克隆到绑定路径。
**动作**：B 机执行下行。
**断言**：
1. 下行**中止**，给出可操作提示「请先把仓库 clone 到 `<repo-path>`」
2. **没有**任何会话被写入（不产生指向不存在目录的僵尸会话）
3. B 机原有数据未变化
4. 用户补齐 clone 后重试 → 正常工作

### AC-2 增量而不是全量

**前置**：AC-1 已完成（B 机已有 3 轮）。
**动作**：B 机追加 **2 轮** → B 上行 → A 下行。
**断言**：
1. A 机能读到**完整 5 轮**
2. A 机**没有重复**任何一轮（不是把 5 轮全部重写，而是 3 + 2 合并）
3. **增量性由内容寻址集合证明**：比对同步分支树的 `{path → blob oid}` 集合
   - 第二次上行后：`shared` 覆盖**全部旧分块**、`added` 数 == 本次新增分块数、`removed == 0`
   - 反面对照（必须能变红）：若实现退化为全量重写，`shared` 骤降且 `removed > 0`

> **为什么不用「字节数明显小于」（原表述，已废弃）**：
> ① 「明显」没有阈值，不可测；② 字节数受 zstd 压缩率影响不稳定——
> 同一批事件因分批方式不同，压缩后可能差一个数量级，无法作为判据。
> 内容寻址的 oid 集合是**确定性**的，与压缩率无关。
> *（已实测验证：真增量 shared=4/added=1/removed=0；全量重写 removed>0，能正确变红）*

### AC-3 冲突：绝不静默覆盖

**前置**：A、B 两端都有同一会话（3 轮）。
**动作**：A 追加 1 轮 → A 上行 → B 也追加 1 轮 → B 上行 → A 下行。
**断言**：
1. A 机**检测到冲突**，本次下行**没有写入**该会话
2. A 机弹出/展示冲突列表，包含双方的分叉位置
3. 用户选择任一处理后，**被放弃的那一份在备份目录中可完整恢复**
4. 全程**没有任何一端的数据被静默丢弃**

### AC-4 可见性：public 需知情确认

**动作/断言**：
1. 对一个 `public` 仓库点「添加绑定」→ 默认**不可**完成绑定，展示风险说明
2. 不输入仓库名 → 无法继续；输入错误的仓库名 → 无法继续
3. 逐字输入正确仓库名 → **可以绑定并启用**
4. **此后连续两次上行都成功**（验证 consent 长期有效，不是每次都拦）

### AC-5 可见性：安全退化必须中止

**动作/断言**：
1. 仓库当前为 `public` 且用户已完成知情确认 → 上行成功
2. 把仓库改为 `private`，再**改回 `public`** → 第三次上行
3. 断言：第三次上行**被中止**，给出明确告警，并要求**重新确认**
4. 断言：中止发生时，**远端没有被写入任何新内容**

> 这条是 §6.4 的核心验收。它证明「consent 绑定的是可见性指纹」而不是一个永久开关。

### AC-6 可见性判定失败不得静默放行

**动作/断言**：
1. 在无网络 / 无 `gh` / 非 GitHub 仓库的情况下尝试绑定
2. 断言：判定结果为 `unknown`，**默认不可启用**
3. 断言：用户必须**主动确认**后才能启用
4. 断言：**下一次上行**仍然要求重新确认（`unknown` 不绑定 consent）

### AC-7 备份前置

**动作/断言**：
1. 构造「备份目录不可写」的场景，执行下行
2. 断言：下行**中止**，返回 `backup-failed`
3. 断言：本地会话目录的**文件内容 hash 集合**与**目录项集合**未发生变化

> **断言维度说明（来自与架构的交叉核对，勿改回 mtime）**：
> **不要用 `mtime` 作为断言维度。** 理由：mtime 精度依文件系统而异
> （1 秒 vs 纳秒），「备份失败 → 立刻断言」这类用例中文件可能**确实被改了但没跨秒**，
> 导致**假绿**。正确维度是：
> - **内容 hash**（每个文件逐个比对）
> - **目录项集合**（`readdir` 前后相同，能抓「新建/删除」；`mkdir` 会改父目录
>   mtime，反而不适合用 mtime 判断"有没有被创建"）
>
> 边界说明：本场景是「**全部被拒绝、无任何合法写入**」，所以可以用 hash 严格断言。
> 这一点与 AC-11 不同，**不要互相照搬**。

### AC-8 恶意/畸形输入被拒绝且本机不变

**动作**：构造畸形包（路径穿越的 session id、超限大小、损坏的压缩帧、不连续的 `seq`）。
**断言**：
1. 全部被**安全拒绝**，给出可读错误（不是崩溃、不是英文栈）
2. 本机会话目录**未发生任何变化**（前后内容 hash 一致 + 目录项集合一致）

> **边界说明**：本用例场景是「**全部被拒绝、无任何合法写入**」，
> 所以能用 hash 做严格断言。这与 AC-11 的场景不同（那边 DSH 自身在持续追加），
> **不要互相照搬**。

### AC-9 锚点提示

锚点有四种状态，**必须分别断言**（对应 design §6.3）。只测「落后」一种不够。

| # | 构造 | 断言 |
|---|---|---|
| **AC-9a 落后** | A 在 commit `X` 产生会话 → 上行 → B 机 HEAD 前进 N 个提交 → 下行 | 展示锚点 `X`、当前 HEAD、**落后数 N**（`git rev-list --count X..HEAD`）|
| **AC-9b 相等** | 两端 HEAD 相同 | 不显示过期提示（**不要无谓打扰**）|
| **AC-9c 非祖先**（rebase / 强推） | A 在 `X` 产生会话 → B rebase 掉 `X` → 下行 | 提示「锚点已不在当前分支历史中」，**不是**静默当成「落后 N 个」 |
| **AC-9d 本地缺 commit** | 锚点 commit 在 B 机不存在（未 fetch） | 提示「未找到锚点提交，请先 fetch」，**不报错、不崩溃** |

**另断言**：即便锚点严重过时，**会话内容仍可正常同步与打开**——
锚点只是**提示**，绝不阻断（design §6.3）。

### AC-10 机器配置复用

**断言**：
1. `~/.ssh/config` 已有的主机，绑定流程中**不需要重填** host / user / port / 私钥
2. 绑定表**不包含**任何凭据或连接四要素
3. 本产品对 `~/.ssh/config` 的**默认行为是一行都不写**

### AC-10b 分支不产生第二个绑定（§4.4）

**动作**：同一仓库，先绑定时在 `main`，切到 `feature-x` 后再次同步。
**断言**：
1. 绑定表里该仓库**仍然只有一条记录**（`repoKey` 相同），**不出现第二个绑定**
2. 切分支前后产生的会话，**都归到同一个绑定**的同步集合
3. manifest 里**记录了分支**作为提示字段，但**它不参与 `repoKey` 计算**
4. 切回 `main` 后，视图与切分支前一致（无身份漂移）

> **反面对照（必须能变红）**：若实现用 `remote + branch` 做键，
> 本条第 1 条断言必然失败（会出现两条绑定）——这正是当前实现的状态。

### AC-11 不碰用户真实数据（兜底哨兵）

> **本条已于交叉核对后修正。原表述「真实 harness home 的 mtime 与 hash 未发生变化」
> 按字面必然失败，与实现无关——已废弃，理由见下。**

**为什么不能用整体 hash**：DSH 自己运行时会持续向 harness home 追加会话。
实测（20 秒间隔、期间**无任何测试运行**，两次独立采样）：**7~9 个会话文件内容发生变化**
（数量随用户正在多少个会话里活动而变，这正是它不可作断言的原因）。
只要用户跑测试时 DSH 是开着的（几乎必然），整体 hash 断言**每秒都会红**。
这种测试的结局通常是被注释掉——表面上「有护栏」、实际零保护。

**正确的主防线是隔离，不是这条哨兵**：
测试必须使用隔离的临时 harness home（见 §8 开头）。隔离到位后，
本条退化为一条**廉价的兜底检查**。

**断言（两条不变量，在 DSH 运行中也稳定）**：

1. **append-only 不变量**（针对会话日志）：
   测试期间若有 `session.*.jsonl.zstd` 发生变化，**旧字节必须是新字节的前缀**。
   → 能抓住「测试写坏了用户会话」，同时容忍 DSH 自己的正常追加。
   *（已实测验证：同一次采样中 7 个变化文件，前缀不变量 **7/7 成立**；
   这不是巧合——它正是日志「仅追加」语义的直接体现）*
2. **路径集合不变量**：
   `~/.dsh/sessions/**` 的**路径集合**不得出现测试新建的条目；
   `~/.dsh` 下不得出现测试创建的任何新文件（备份目录、临时文件等）。

> **交叉核对记录**：本条由架构（`docs/prd-assertion-crosscheck.md` 冲突 1）提出，
> 产品侧独立复现后采纳。原「hash 不变」的维度**太强**（必然误报），
> 换成上述两条**能稳定区分对错**的不变量。

### AC-12 代码不被触碰

**断言**：任何同步操作后，**以下五项全部未变**：

1. **工作区状态**：`git status --porcelain` 前后相同
2. **分支与 ref 指针**：用户自己的分支指针不变
   （同步可在**私有 ref** 如 `refs/dsh-sessions/*` 下创建提交，这不算改动用户数据）
3. **stash 列表**：`git stash list` 相同
4. **未跟踪文件集合**：相同
5. **用户 commit 历史不被改写**：`git rev-list --all` 的 oid 集合**包含关系不变**

> **为什么补第 2、5 条**：只断言 `git status` 是不够的。如果实现对用户分支
> 做了 rebase 或强推，**工作区看起来是干净的**，但历史已被改写——`git status`
> 测不到这种情况。用户的分支指针与历史是不可再生数据，必须单独断言。

> **一句话**：本产品不产生任何代码改动、不 commit 用户代码、不 push 用户分支。

## 10.1 与 `docs/testing-assertions.md` 的交叉核对

本节的 AC **不是**「产品想看到什么」的散文，它们要能被转写成可执行的断言。
架构已做逐条交叉核对，结果见 [`docs/prd-assertion-crosscheck.md`](./prd-assertion-crosscheck.md)。

**核对结论：9 条原样采纳、3 条换了度量维度、0 条被删除。**
被改的三条**不是内容错，是「验收方式在工程上落不了地」**：

| AC | 原维度（已废弃） | 换成 | 为什么原维度不行 |
|---|---|---|---|
| **AC-11** | 真实 harness home 的 **hash 不变** | append-only 前缀 + 路径集合不变 | 维度**太强**：DSH 自身持续追加，必然误报 → 测试会被注释掉，护栏形同虚设 |
| **AC-7** | mtime + hash | **只留 hash + 目录项集合** | 维度**太弱**：mtime 精度依文件系统而异，会**假绿** |
| **AC-2 第 3 条** | 字节数「明显小于」 | 内容寻址 oid 集合（shared/added/removed）| 「明显」无阈值；字节数受 zstd 压缩率影响不稳定 |

> **本轮最重要的经验**：
> 断言要选**能稳定区分「对」与「错」**的维度，**不是选「看起来最严格」**的维度。
> AC-11 选了太强的（必然误报），AC-7 选了太弱的（会漏报）——
> 两条看上去都很严格，实际都不能用。

**产品侧已独立复现验证**（不采信二手结论）：

| 核对项 | 验证方式 | 结果 |
|---|---|---|
| DSH 运行时 harness home 是否变化 | 20 秒间隔只读采样，期间无测试 | **9 个会话文件变化**，确认原 AC-11 必然误报 |
| append-only 前缀不变量是否成立 | 同上采样 + 前缀比对 | **7/7 成立**，可作稳定断言 |
| oid 集合能否区分增量/全量 | 内容定义分块复现 | 真增量 `shared=4/added=1/removed=0`；全量重写 `removed>0` → **能正确变红** |

### B.2 关于「写盘 ≠ 可见」的证据

这条发现改变了 MVP 的定义，故把证据链留档，避免后人重新踩坑。

| # | 事实 | 证据位置 |
|---|---|---|
| 1 | 侧栏的会话列表来自工作区注册表的 `sessionIds`，**不是扫盘** | `dsh-api-workspace-controller` 的 workspace 序列化只输出 `sessionIds` |
| 2 | `sessionIds` 只在两个时机写入：`bootstrap()`（仅当 `initialized === false`）与 `attachSession()`（仅 DSH 自建会话时调用） | `dsh-workspace/lib/index.js` |
| 3 | 正常用户机器 `initialized` 已是 `true`，**`bootstrap` 永不再跑** | 同上，`Service.init()` 的守卫分支 |
| 4 | 即使登记成功，`cwd` 不匹配仍会被**主动剔除** | `reportFilteredCandidates()` 的 `candidateMatches(sessionId, record.path)` |
| 5 | 实测：磁盘 218 个会话，注册表仅登记 45 个 | 本机只读统计 |

**结论**：下行必须同时解决「登记」与「`cwd` 重写」两件事，**缺一不可见**。
