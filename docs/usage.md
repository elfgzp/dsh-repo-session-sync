# 使用指南

> 从零开始，把一台机器的 DSH 会话同步到另一台机器。
>
> 本文所有示例都使用占位符：`~/my-project`、`user@host`、`192.0.2.10`（这是专门给文档用的保留 IP 段，不指向任何真实机器）。请替换成你自己的值。

---

## 0. 先理解这件事在做什么

换机器时，**代码有 `git commit` / `git push` 可以同步，AI 会话没有。**

这个插件补上缺的那一半：

- **代码** → 继续用你自己项目的 git，插件不碰你的工作区、不替你 commit。
- **会话** → 由本插件同步，并且知道「这段对话当时对应的是哪个 commit」。

所以它的正确用法是：**先把代码推上去，再同步会话。** 顺序反了会出现"会话里说改了 A，但对面 `git pull` 下来没有 A"——那个问题 git 自己解决不了，插件也不应该假装能解决。

> 💡 一句话：**这不是一个「备份 ~/.dsh」的插件。** 它只同步你绑定过的 git 仓库相关的会话，其他东西（设置、插件、skills、别的目录的会话）一概不动。

---

## 1. 前置条件

| 条件 | 怎么确认 |
|---|---|
| 两台机器都装了 DSH | `dsh --version` |
| 两台机器都装了本插件 | `dsh plugin list \| grep repo-session-sync` |
| 你的项目是一个 **git 仓库**，且有 **remote** | `git remote -v` |
| 你**能在这台机器上手动 `git push`** | `git push` 试一次 |

最后一条是核心：**能 `git push` 就能同步**。插件不保存任何令牌、密码、私钥——它用的是你自己系统的 git 凭据（macOS 钥匙串、SSH agent、credential helper）。

> 🔐 **插件不读、不存、不回显任何凭据。** 如果某一步问你密码，那是 `git` 或 `ssh` 在问，不是这个插件在问。

---

## 2. 安装

在两台机器上分别执行：

```bash
dsh plugin add dsh-repo-session-sync
```

或者从本地源码装（改代码调试时用）：

```bash
dsh plugin add ~/my-plugins/dsh-repo-session-sync
```

装完重启 DSH，设置页会出现「会话同步」一节。

**验证装好了：**

```bash
dsh plugin list | grep repo-session-sync
```

---

## 3. 绑定一个仓库

> 这一节在两台机器上**都要做**。绑定关系存在各自的机器上，不随同步传输（它是本机的配置，不是会话内容）。

1. 打开 **设置 → 会话同步**
2. 点 **「添加仓库」**，选择你的项目目录（例如 `~/my-project`）
3. 插件会读出这个目录的 git remote 地址，确认无误后保存
4. 选择同步方向：**上行** / **下行** / **双向**

保存后，这一行会显示：

- 仓库路径与 remote
- 当前分支
- 同步方向
- **待同步数量**（本机有多少条新对话还没推上去）
- 最近一次同步的时间与结果

### 关于同步方向怎么选

| 方向 | 含义 | 适合谁 |
|---|---|---|
| **上行**（up） | 只把本机会话推上去 | 这是你的主力机器 |
| **下行**（down） | 只把远端会话拉下来 | 这是你的次要机器，通常只看不写 |
| **双向**（both） | 两边都同步 | 你在两台机器间交替使用（最常见） |

> ⚠️ **「双向」不是"自动挑新的覆盖旧的"。** 两端都改过同一个会话时，插件**不会静默覆盖任何一边**，而是保留两份并提示你处理。见 [第 6 节](#6-冲突了怎么办)。

---

## 4. 触发同步

三种方式：

1. **设置页按钮** —— 每个仓库一行，「上行」「下行」（方向为 `both` 时两个都可用）
2. **对话里让 Agent 做** —— 例如「把这个仓库的会话推上去」
3. **自动同步** —— 目前**默认关闭**，也不在 MVP 范围内。需要手动触发。

**推荐节奏：**

```
改完代码 → git commit && git push → 同步会话（上行）
换到另一台机器 → git pull → 同步会话（下行）
```

> ⚠️ **顺序很重要。** 先推代码再推会话。反过来的话，会话说「我改了 A」，
> 但对面 `git pull` 下来没有 A —— 这个错位 git 自己解决不了，插件也不该假装能解决。

### 为什么会话不跟着 `git clone` 过来

会话数据存在仓库的一个**独立引用**里（`refs/dsh-sessions/v1`），不在普通分支上。
这是刻意的：

- `git push --all` **不会**顺带推它
- 别人 `force-push` **动不了**它
- `git gc --prune=now` **清不掉**它
- 删分支也**不影响**它

代价是：**全新 `git clone` 不会带出会话。** 这是最容易让人以为"同步坏了"的地方。

新机器第一次同步时，用插件里的「下行」就行。如果你想手动做，等价命令是：

```bash
cd ~/my-project
git fetch origin 'refs/dsh-sessions/v1:refs/dsh-sessions/v1'
```

## 5. 在两台机器之间实际走一遍

假设你有 `desk`（台式机）和 `laptop`（笔记本），项目叫 `demo-repo`。

### 5.1 第一次：把 desk 上的会话带到 laptop

**在 desk 上：**

```bash
cd ~/my-project
git add -A && git commit -m "wip: 今天的改动"
git push
```

然后：设置 → 会话同步 → `demo-repo` 那一行 → **上行**。
第一次会先给你看**预览**（「将同步 N 个会话，共 X KB」）—— 因为上行是把私密数据推出去，
不可撤销（内容已经离开本机了），所以这一步不省。确认后才真正推。

**在 laptop 上：**

```bash
cd ~/my-project
git pull
```

然后：设置 → 会话同步 → **添加仓库** → 选 `~/my-project` → **下行**。

下行比上行慢一点，因为它在写任何东西之前会**先给本机会话目录做一份快照**。

完成后你会看到：
- 「已拉取 N 个会话」
- 如果本机已有同名会话，会显示冲突提示（见 §6）

### 5.2 ⚠️ 两台机器的仓库路径不一样，是没问题的

这是**常见**情况，不是异常：

| 机器 | 仓库位置 |
|---|---|
| desk | `~/my-project` |
| laptop | `~/work/projects/my-project` |

**能对上的原因**：仓库身份由 **remote 地址 + 分支**决定，不由文件系统路径决定。

**但插件必须替你处理一件事**：会话里记录的「我是从哪个目录启动的」是 A 机的路径。
下行到 B 机时，这个路径会被**改写成 B 机的真实仓库路径**。

为什么必须改（不是可选的美化）：
1. **可见性**：DSH 的会话列表会过滤掉 `cwd` 与工作区路径不一致的会话 —— 不改写的话，会话写进了磁盘但**界面里看不到**。
2. **安全**：不改写的话，你在 B 机继续这个对话时，工具会在 **A 机的路径语义下**执行 —— 落在错误的目录里。这是真实风险，不是体验问题。

**如果 B 机还没 clone 这个仓库**，下行会**中止**并提示你先 clone。
它**不会**写入一个指向不存在目录的会话 —— 那种"打开就报错"的僵尸会话会随着下次上行
扩散回其它机器，污染是双向的。

### 5.3 验证同步成功（别只看「成功」两个字）

同步结果显示成功，不代表你能用。**按这个顺序验证：**

1. 打开 DSH 的会话列表
2. 找到对应仓库下的那个会话
3. **点开它，确认能正常渲染**
4. 说一句话，确认能继续对话、正常保存

> 这一步不是多余的仪式。会话文件写到磁盘上、和它出现在界面里，是两件事。
> 如果第 2 步看不到，说明路径改写没生效 —— 请按 §9 反馈。

### 5.4 之后：交替使用

```
desk 上聊几句  → 上行
laptop 上 git pull → 下行 → 接着聊
laptop 上聊几句 → 上行
desk 上 git pull  → 下行 → 接着聊
```

每次只传**新增的部分**（增量），不是整个会话重传。

## 6. 冲突了怎么办

冲突发生在：**两台机器都改过同一个会话**。

插件**绝不会**替你做决定，也**不会**自动合并对话 —— 自动合并等于伪造一段从未发生过的对话历史。

你会看到类似这样的提示：

> 「有 3 个会话在两台机器上都有新内容。为避免丢内容，两边都完整保留了，没有覆盖任何一边。」

处理方式：

| 情况 | 建议 |
|---|---|
| 其中一边只是打开看了一下，没实际对话 | 保留有实际对话的那份 |
| 两边都有实质内容 | **两份都留着**，之后手动挑 |
| 不确定 | **先都留着。** 两份都在，随时能回来处理；覆盖了就真没了 |

> 🔒 **安全保证**：任何覆盖本机会话的操作都要求**二次确认**，写入前**一定先做快照**。
> 设置页有「还原」入口，可以退回到同步前的状态。

## 6.5 仓库可见性：这是最需要你留意的安全闸门

**同步 = 把完整对话内容推到远端仓库。**

包括：你本机的路径、命令输出、代码片段，以及你在对话里贴过的任何东西。

所以绑定仓库时，插件会先查这个仓库是**私有**还是**公开**：

| 判定 | 插件行为 |
|---|---|
| **私有** | 直接放行 |
| **公开** | **默认阻止**。要继续，必须**逐字输入仓库名**确认你了解后果 |
| **查不到**（没网 / 非 GitHub / 没权限） | **默认阻止**。同样需要逐字确认 |

**「查不到」绝不等于「安全」** —— 这是这条设计里最重要的一句话。

### 推荐做法：用私有仓库

如果你看到「这个仓库是公开的」，最省事的处理是把仓库改成私有：
GitHub → 仓库 → Settings → General → 最下面 Danger Zone → Change visibility → Make private。
改完回到设置页点「重新检测」。

### 如果你确实要推到公开仓库

输入仓库名确认之后可以绑定。但请再看一遍上面那句话：**任何人看到这个仓库就能读到那些对话。**

### 每次上行前都会重新检查

这一点值得单独说明。仓库今天私有，明天可能被改成公开 —— 只在绑定时查一次等于
「装了个只响一次的警报器」。

所以**每次上行前都会重判一次**，判断的是「**有没有偏离你当初确认的那一种**」：

| 你确认时的可见性 | 本次判定 | 结果 |
|---|---|---|
| 私有 | 私有 | ✅ 放行 |
| 私有 | **公开** | ❌ **中止 + 告警**（最危险：悄悄变公开了） |
| 私有 | 查不到 | ❌ 中止（查不到不等于安全） |
| 公开（你确认过） | 公开 | ✅ 放行 —— 你确认过就是确认过，不会每次拦你 |
| 公开（你确认过） | 私有 | ✅ 放行（变得更安全了） |
| 查不到 | 任意 | ❌ 中止，每次都要重新确认（查不到没有可绑定的依据） |

## 7. 机器配置：正常情况下你不需要配任何东西

> 用户原话里有一句「**参考 remote 方式配置好机器**」。
> 这一节解释插件是怎么回应这个要求的 —— 结论可能和你预期的不一样：
> **最好的机器配置，是不需要配置。**

### 7.1 默认行为：零配置

**同步走的是仓库自己的 git remote。** 这个地址已经在你的 `.git/config` 里了——
插件不需要你再填一遍主机、用户、端口、私钥。

认证也沿用你**已经配好的** git 凭据（macOS 钥匙串 / SSH agent / credential helper）。
插件**不保存任何凭据**，因为根本没有第二份凭据需要它保存。

判断标准只有一条：**你在这台机器上能手动 `git push` 吗？** 能，就配好了。

```bash
cd ~/my-project && git push
```

失败的话先修这个 —— 插件帮不了你，也不该帮你（它能做的只是重复一遍 ssh 的活，
然后多出一个会和 `~/.ssh/config` 漂移的副本）。

**默认情况下，插件对 `~/.ssh/config` 一行都不写。**

### 7.2 如果你已经在用 `~/.ssh/config`

插件会**只读**这个文件，用来给「新建机器」的下拉框提供候选（只列 Host 名字，不读私钥、不回显任何连接信息）。

已有的 Host 别名可以直接用：

```sshconfig
# ~/.ssh/config 里你原本就有的配置
Host myserver
  HostName 192.0.2.10
  User dev
  IdentityFile ~/.ssh/id_ed25519
```

在设置页里选 `myserver` 就行，插件不会改这一段。

### 7.3 如果你让插件新建一台机器

只有在设置页点「新建机器」时，插件才会往 `~/.ssh/config` **追加**一个带标记的块：

```sshconfig
# dsh-repo-session-sync: managed
Host myserver
  HostName 192.0.2.10
  User dev
  Port 2222
```

规则（这些是硬保证，不是"尽力而为"）：

- ✅ 只改**自己标记**的块，**绝不碰你手写的块**
- ✅ 如果已经有一个**你手写的**同名 Host，插件报冲突并**原文一字不改**
- ✅ 块里你自己加的行（比如 `ForwardAgent yes`、注释）在插件更新时**保留**
- ✅ **删掉一台机器不会删 `~/.ssh/config` 里的块** —— 那是你的 SSH 通道，不是插件的状态

> ⚠️ **重要：不要同时用两个插件管理同一批机器。**
>
> 如果你还装了 `dsh-remote`，请注意它的受管块标记是 `# dsh-remote: managed`，而我们的是 `# dsh-repo-session-sync: managed`。
>
> **两个插件各写各的受管块时，会互相把对方的块判定为"用户手写的配置"，于是双方都拒绝更新。** 结果不是报错，而是"明明配了却改不动"——很难排查。
>
> 建议：**同一台机器只让一个插件管它的 SSH 配置。** 我们推荐让 `dsh-remote` 管（它就是干这个的），我们这边只用 `git push`。

### 7.4 常见的 SSH 报错

| 你看到 | 实际含义 | 怎么办 |
|---|---|---|
| `Permission denied (publickey)` | 公钥认证被拒 | 把 `~/.ssh/id_*.pub` 内容追加到远端 `~/.ssh/authorized_keys` |
| `Host key verification failed` | 主机指纹变了/没见过 | 先在终端 `ssh myserver` 手动确认一次；**如果指纹不该变，先别连** |
| `Could not resolve hostname` | 名字解析不了 | 检查 `~/.ssh/config` 里的 `HostName` |
| `Connection timed out` | 网络不通 | 确认机器在线、端口对，以及是否需要 VPN / 跳板机 |

## 8. 常见问题

**Q：会同步我的 DSH 设置、插件、skills 吗？**
不会。只同步绑定过的 git 仓库相关的**会话内容**。设置/插件同步是另一个产品
（`dsh-settings-sync`）的职责，混在一起会让「同步会话」这件事的认知负担变重。

**Q：会同步非 git 目录里的会话吗？**
不会。没有 git remote 的目录没有"仓库身份"，无法跨机器对应。明确不支持，
比"支持了但经常对不上"好。

**Q：会话里的附件/图片会同步吗？**
**不会，MVP 默认不同步附件。** 会话正文会同步。

原因是一个实测数据：本机 218 个会话里，181 个（83%）的文本中出现 `attachment` 字样，
但**真正指向附件存储的只有 5 个（2.3%）** —— 其余绝大多数是工具 schema 里的字段名，
不是真实引用。为 2.3% 的场景引入二进制对象搬运、去重与 GC，投入产出不匹配。

**如果某个会话带附件，同步结果里会明确点名「该会话含附件，未同步」**，不会静默丢弃。

**Q：子代理（subagent）的会话会同步吗？**
MVP **只同步根会话**。子会话是父会话的执行过程，不是用户想「继续」的对话。

实测依据：某仓库 35 个会话中 30 个是子会话，占 **77% 的字节量**（76.8MB / 99.9MB）。
同步它会让传输成本翻三倍以上，而价值接近于零。

你在界面上数到的「N 个对话」也是只算根会话 —— 这样数字才和你的直觉一致。

**Q：我在 A 机器删了一个会话，会同步到 B 吗？**
不会。删除是本地操作，不传播。这也是刻意的——跨机器删数据风险太高。

**Q：仓库改名了 / 换 remote 地址了怎么办？**
插件按 remote 地址识别仓库身份。改了地址，需要在设置页重新绑定一次（旧绑定会被认成另一个仓库）。

**Q：分支切换了会怎样？**
会话与分支是关联的。切到别的分支后，这个分支的会话不会被误同步过去。

**Q：能同步到团队的共享仓库吗？**
技术上可以，但**不要**。会话内容通常包含你本机的路径、命令输出、可能的敏感信息。用你自己的仓库。

**Q：同步失败会弄坏我的会话吗？**
下行写入前一定先做快照；校验不通过就完全不写。上行只读不写本机会话。

## 9. 出问题了怎么排查

1. **先看设置页那一行**：最近一次同步的结果和错误原因都显示在那里
2. **确认 git 本身能通**：`cd ~/my-project && git push` —— 如果这一步就失败，插件帮不了你
3. **确认插件装好了**：`dsh plugin list | grep repo-session-sync`
4. **看 DSH 日志**里的 `repo-session-sync` 前缀

如果错误提示看不懂，说明是我们的文案没写好——请开 issue 告诉我们那句话。
