# PRD 验收标准 ↔ E2E 断言口径 交叉核对

> 两份文档由不同角色并行编写、互相没看过：
> - [`docs/prd.md`](./prd.md) §8 定义了 **AC-1 ~ AC-12**（产品视角：用户看到什么）
> - [`docs/testing-assertions.md`](./testing-assertions.md) 定义了 **A–G 七组**（工程视角：怎么判定）
>
> 本文做交叉核对，找出三类问题：
> 1. **冲突** —— PRD 的某条按字面无法测出，或与工程口径矛盾
> 2. **遗漏** —— PRD 没要求但工程上必须测的
> 3. **缺口** —— 工程断言没覆盖 PRD 要求的
>
> **这类问题比代码 bug 更隐蔽**：代码 bug 在测试时就暴露，文档不一致要到最终验收才爆发。

## 结论摘要

| 类型 | 数量 | 处理 |
|---|---|---|
| 🔴 **必须修改 PRD**（按字面测不出来 / 已实测证伪） | **2 条** | AC-11、AC-7 |
| 🟡 **必须修改断言文档**（PRD 要求了但断言没覆盖） | **3 条** | AC-9、AC-12、可继续对话 |
| 🟢 **两边一致，仅需互相引用** | 其余 | 加交叉链接 |
| ⚪ **PRD 正确但断言文档表述需收紧** | 1 条 | AC-8 |

## 🔴 冲突 1：AC-11「真实的 harness home 的 mtime 与 hash 未发生变化」

**PRD 原文**：
> **断言**：整套测试跑完后，**真实的 harness home 的 mtime 与 hash 未发生变化**。

**问题：这条按字面写，**必然失败**，与实现无关。**

**实测证据**（对真实 `~/.dsh` 只读采样，间隔 20 秒）：

```
t0  hash: 1437d90e…c7d5
t20 hash: 71c5c25c…4c51
changed: YES
```

**在这 20 秒里没有任何测试运行**——变化来自 **DSH 本身正在运行**（当前对话就在往
`~/.dsh/sessions/` 写）。也就是说：

> 只要用户在跑测试时 DSH 是开着的（几乎必然），`~/.dsh` 的 hash **每秒都在变**。
> 这条断言会把「DSH 正常工作」判成「测试污染了用户数据」。

**这与我在 `docs/testing-assertions.md` C4 已经记录的反模式是同一条**：

| 反模式 | 为什么错 |
|---|---|
| 断言 `~/.dsh` 前后 hash 完全不变 | DSH 运行时持续 append，必然 flaky |

**建议改法**：把「hash 不变」换成**两条可断言的不变量**：

1. **append-only 不变量**（针对会话日志）：测试期间若某个
   `session.v4.jsonl.zstd` 发生了变化，旧字节必须是新字节的**前缀**。
   —— 这能捕获「测试写坏了用户会话」，同时容忍 DSH 自己的正常追加。
2. **测试不得新增会话 / 不得新增文件**（针对文件集合）：
   测试前后 `~/.dsh/sessions/**` 的**路径集合**不得出现测试新建的条目；
   `~/.dsh` 下不得出现测试创建的任何新文件（如备份目录、临时文件）。

这两条合起来，才能真正表达 PRD 想要的「不碰用户真实数据」，
而且**在 DSH 运行中也稳定**。

> **替代方案（更彻底）**：测试**强制使用隔离的 `DSH_HOME`**（PRD §8 开头已经要求了
> 「测试一律使用隔离的临时 harness home」）。如果隔离真正做到位，
> 断言「真实 home 未被触碰」就退化成一条**廉价的兜底**——
> 此时可以只断言「真实 home 下的文件**路径集合**不变」，不必比 hash。
>
> 两个要求（隔离 + 兜底）叠起来才有意义：**隔离是主防线，hash 断言是哨兵。**
> 但哨兵不能是 hash（会误报），应该是「路径集合不变」。

## 🔴 冲突 2：AC-7「本地会话目录的 mtime 与内容 hash 未发生任何变化」

**PRD 原文**：
> 3. 断言：本地会话目录的 mtime 与内容 hash **未发生任何变化**

**问题：mtime 是不可靠的断言维度。**

- 「备份失败 → 中止」这条路径下，实现可能**先创建了备份目录**再失败，
  或先算过 hash / 读过文件——**读操作本身不改 mtime，但 `mkdir` 会改父目录 mtime**。
- 更实际的：**mtime 精度与文件系统有关**（有的 fs 是 1 秒粒度，有的是纳秒）。
  对「中止后立刻断言」的用例，1 秒粒度会导致**假绿**（变化了但没跨秒）。

**建议改法**：只断言**内容 hash 不变**，删掉 mtime。
如果确实想验证「没有被创建/删除」，用**目录项集合**（`readdir` 前后相同）比 mtime 可靠得多。

> 这条与「AC-11 用 hash」形成有趣对比：**AC-11 该用更弱的断言（hash 太强会误报），
> AC-7 该用更弱的断言（mtime 太弱会漏报）。** 两条都指向同一个工程原则：
> **断言要选能稳定区分「对」与「错」的维度，而不是选看起来最严格的维度。**

## 🟡 缺失 1：PRD 要求「能继续对话」，但断言文档没覆盖

**PRD AC-1 第 3 条 + AC-1b 第 3 条**：
> 3. **B 机能在这个会话上继续对话**，新增内容正常落盘
> 3. B 机继续对话时，工具调用落在 `B` 目录下（**不在 A 的路径语义下**）

**断言文档 A–G 七组里没有对应条目。** 这是**真实的验收缺口**——
「能打开」和「能继续」是两回事：

- 能打开：`attachSession` 成功、出现在列表
- 能继续：DSH 能在这个会话上追加事件，且**追加后的 seq 接得上**

**建议新增断言（我在断言文档里补为 E5）**：

**E5 — 下行后可继续对话，且 seq 连续衔接**
1. 下行完成后，模拟 DSH 的追加：向该会话写入一个新事件（`seq = 已同步的最后 seq + 1`）
2. 断言：写入成功、文件可正常解码、`nextSeq` 正确递增
3. 断言：新事件所在会话的 `header.cwd` 仍是 **B 机路径**（不是被同步过程改回 A 机）
4. 断言：工具调用的执行目录语义属于 B 机（可用 `git -C <cwd> rev-parse --show-toplevel`
   验证 cwd 确实指向 B 的仓库）

**为什么这条必须有**：如果下行写入的 `nextSeq`/末尾状态不对，DSH 后续追加会失败或产生
seq 冲突。**"能打开但不能继续"是比"打不开"更糟的失败**——用户会以为同步成功了，
在继续工作时才发现会话坏了。

## 🟡 缺失 2：PRD AC-9 锚点提示，断言文档完全没有覆盖

**PRD AC-9**：
> 在 commit `X` 产生会话 → 上行 → B 机把 HEAD 切到 `Y` → 下行。
> 断言：B 机展示「该会话基于 `X`，当前 HEAD 是 `Y`」。

**断言文档 A–G 七组里没有任何一条覆盖锚点。** 而设计 `docs/design.md` §6.3 明确定义了
四种锚点状态（祖先落后 N 个 / 相等 / 非祖先 / 本地缺 commit）及各自提示文案。

**建议新增断言（补为 H 组）**：

**H1 — 锚点落后提示**
- 构造：A 在 commit `X` 产生会话 → 上行 → B 拉取后 `HEAD` 前进 N 个提交 → 下行
- 断言：返回结果里包含锚点 `X`、当前 `HEAD`、以及**落后提交数 N**
  （`git rev-list --count X..HEAD` 的值）

**H2 — 锚点非祖先（rebase / 强推）**
- 构造：A 在 commit `X` 产生会话 → B rebase 掉 `X` → 下行
- 断言：提示「锚点已不在当前分支历史中」（不是静默当成"落后 N 个"）

**H3 — 本地缺锚点 commit**
- 断言：提示「未找到锚点提交，请先 fetch」，**不报错崩溃**

**H4 — 锚点只是提示，绝不阻断**
- 断言：即便锚点严重过时，会话内容仍然可同步、可打开
  （设计 §6.3：「只在 UI 提示，绝不阻断」）

## 🟡 缺失 3：PRD AC-12「代码不被触碰」只覆盖了工作区，断言 C 组可更完整

**PRD AC-12**：
> 断言：任何同步操作后，目标仓库的工作区状态（`git status`）**未发生变化**

**断言文档 C2** 已覆盖（`git status --porcelain` 前后相同）。但 PRD 只提了工作区，
而**真正的风险面更大**：

**建议把 C1/C2/C3 明确标注为 AC-12 的实现**，并补充：

**C5 — 用户的分支指针 / stash / 未跟踪文件全部不变**
- `git for-each-ref` 逐字节相同（C1 已含）
- `git stash list` 相同
- 未跟踪文件集合相同

**C6 — 用户的 commit 历史不被改写**
- `git rev-list --all` 的 oid 集合在同步前后包含关系不变
  （同步可能创建新 commit 到私有 ref，但**绝不能改写用户的提交**）

> 这条重要：如果实现不小心对用户分支做了 rebase 或强推，`git status` 可能看起来正常
> （工作区干净），但历史已被改写。**AC-12 的字面要求测不到这种情况。**

## ⚪ 表述需收紧：AC-8「前后 hash 一致」

**PRD AC-8**：
> 2. 本机会话目录**未发生任何变化**（前后 hash 一致）

这条在**恶意输入被拒绝**的场景下是**正确的**（此时没有合法写入）。
但要注意与 AC-11 的区别：

- AC-8 断言的对象是**本机会话目录**，且场景是「全部被拒绝」→ hash 不变是合理期望 ✅
- AC-11 断言的对象是**真实 harness home 整体**，且场景是「整套测试跑完」→ hash 必然变 ❌

**建议在 AC-8 里补一句限定**：「本用例不涉及任何合法写入，故可用 hash 严格断言；
这与 AC-11 的场景不同，不要互相照搬。」

### AC-2 第 3 条需要换度量维度

PRD 写「第二次上行传输的**字节数明显小于**第一次」。
「明显小于」不可测（没有阈值），且**字节数受压缩率影响不稳定**。

**建议改为**接入断言文档的 **B2**：比对 `refs/dsh-sessions/v1` 树的
`{path → blob oid}` 集合变化 —— `added oid` 数应等于**本次新增分块数**，
`removed` 为 0，`shared` 覆盖全部旧分块。这是**确定性**的，不依赖压缩率。

### 断言文档需要补的三组（PRD 要求了，我漏了）

1. **AC-4/5/6 可见性交互**（`repo-visibility.js` 已实现，且我实测过 12/12 通过）：
   - public 默认拒绝 + 逐字确认才放行
   - `private → public` 变化 → 中止并重新要求确认
   - `public → public`（已确认）→ 放行，**不重复骚扰**
   - `unknown` → 不默认放行，且**不绑定 consent**（每次重问）
2. **AC-7 备份前置**：备份失败 → 中止且零写入
3. **AC-10 机器配置**：默认对 `~/.ssh/config` **一行都不写**；绑定表无凭据/四要素

> 这三组我会补进 `docs/testing-assertions.md`（新增 I/J/K 组）。

## 建议的处理顺序

1. **先改 PRD 的两条冲突**（AC-11 换断言维度、AC-7 去掉 mtime）—— 否则实现方会照着
   写出一条**必然 flaky** 的测试，然后在 CI 上反复红绿，最后被注释掉。
2. **补断言文档的三处缺失**（E5 可继续对话、H 组锚点、I/J/K 组）
3. 两边加交叉引用链接

> **最后一条经验**：本轮核对发现的 **2 条冲突全部是「断言维度选错」**——
> AC-11 选了太强的（hash），AC-7 选了太弱的（mtime）。
> 而「看起来最严格」的维度往往不是「最能区分对错」的维度。
