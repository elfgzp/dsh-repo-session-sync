# E2E 断言口径

> 本文定义 `dsh-repo-session-sync` 的端到端测试**应该断言什么、为什么这样断言、
> 以及"实现写错了这条会不会红"**。
>
> **不是给测试代码，是给测试推理。** 判定一条断言能不能留下的标准只有一条：
> **如果实现错了，它会不会红？** 不会红的断言不是断言，是装饰。

## 为什么要有这份文档

本项目的头号教训是**假绿（false green）**：

> 会话日志是独立 zstd 帧的拼接。用 `zlib.zstdDecompressSync(整个文件)`
> **只解第一帧就返回，不报错**——
> 实测 757,118 字节的文件只解出 **273 字节**（真值 3,080,613）。
>
> 而第一帧恰好是 header，header 是**合法 JSON**。
> 于是"能解析出会话头"的断言会**通过**，对话内容一条都没读到。

**这个 bug 的伟大之处在于它不会制造任何异常。** 它只会让用户在两台机器之间
发现"对话少了一大半"，而所有测试都绿着。

所以本文每一条断言都遵循同一个模板：

```
断言什么  →  能防住哪种错误  →  实现错了会怎样（必须红的情况）
```

并要求每条断言**配一个反向对照（negative control）**：故意构造错误的实现行为，
确认断言真的会红。**没有反向对照的断言，视为未经检验。**

## 断言组 A：完整性（防丢数据）

### A1 — 事件流逻辑等价，而非文件字节相等

**断言**：A 机 push 的会话，B 机 pull 后解出的事件序列，与 A 机原始事件序列
**逐事件 `deepEqual`**（`type` / `seq` / `data` 全部字段一致）。

**为什么不是"文件字节相同"**：
下行时 `header.cwd` 必须被重写为 B 机的真实仓库路径（否则 DSH 会过滤掉该会话，
详见 `docs/design.md` §11.3）。重写会改变字节，**字节相同是错的期望**。

**能防住**：静默丢事件、事件字段被裁剪、cwd 重写时顺手改坏了别的东西。

**实现错了会怎样**：
- 只解第一帧（one-shot 解码 bug）→ B 机只有 header、没有事件 → **红**
- 重写 cwd 时重建了事件对象、丢了 `surfaceOp` / `sourceEventSeqs` → **红**

**反向对照（必须有）**：
构造一个"只写入 header 就返回"的假 pull，断言 A1 **必须失败**。

---

### A2 — 数量与边界精确相等

**断言**：`事件数`、`max(seq)`、`首事件 seq`、`尾事件 seq` **精确相等**
（不是"大于等于"，不是"差不多"）。

**能防住**：尾部丢失（只同步了部分帧）、重复追加（seq 出现重复）。

**实现错了会怎样**：
- 水位线算错、少传最后一帧 → `max(seq)` 偏小 → **红**
- 幂等性缺陷导致同一段被推两次 → 事件数偏大 / seq 重复 → **红**

**为什么用 `seq` 而不是数组长度**：
`seq` 是 DSH 自己的不变量（从 0 严格 +1）。长度相等但 seq 有缺口的情况是可能存在的
（例如中间事件被跳过），只有比对 seq 才能抓到。

---

### A3 — 每一帧都必须可解，不允许"跳过坏帧继续"

**断言**：从 B 机落盘文件顺序扫帧，**每一帧**都能独立解出合法 JSONL；
不连续的帧即刻失败；torn tail 只允许出现在**最后一帧**且必须被显式识别丢弃。

**能防住**：把"解不开就跳过"当成容错的实现——这会让数据静默缺失。

**实现错了会怎样**：
- 用"搜索魔数"切帧，把一帧切碎 → 某帧解压失败 → **红**
- 把 torn tail 当损坏直接丢弃整个会话 → 事件数变少 → **同时触发 A2 红**

**注意**：torn tail 是**正常状态**（进程崩溃的中间态），不是损坏。
断言要区分"最后一帧不完整"（允许、丢弃）与"中间某帧不完整"（必须红）。

---

## 断言组 B：增量性（防全量重写）

> 这组断言的依据是设计里最硬的一条实测结论：
> 同一份 20 MiB 载荷、20 次增量提交，**整文件重写 → `.git` 210 MB**，
> **内容寻址分块 → 20 MB**。差 10 倍。
> 如果实现退化成全量重写，用户的**代码仓库会被会话数据撑爆**。

### B1 ⚠️ 不要用"远端对象总数"做断言（实测此路不通）

我实测过这条思路，**它不能区分增量与全量重写**：

```
向远端 push 5 个 blob 后：远端 count-objects = 3
再 push 1 个 blob 后     ：远端 count-objects = 3   ← delta = 0
```

原因是 git 会把松散对象打包，且**未被引用的对象根本不会传到远端**。
用总数做断言会得到**恒绿**的假断言。

**反面教训**：这正是一条"看起来很有说服力、实际什么都测不到"的断言。
写进本文，避免后来者重走。

### B2 — 用「ref 树的 blob OID 集合变化」判增量（推荐做法）

**断言**：记下第一次 push 后 `refs/dsh-sessions/v1` 树的
`{path → blob oid}` 映射；二次 push 后再次取映射，要求：

```
新增 oid 数 <= 本次新增分块数 + 1      （+1 是 manifest）
移除 oid 数 == 0                       （旧分块绝不能被删）
共享 oid 数 >= 旧分块总数 - 1
```

**实测正向**（真实 git plumbing，增量追加 1 块）：

```
oids push1=4  push2=5
shared oids = 4     ← 旧块全部保留
added oids  = 1     ← 只新增 1 块
removed oids= 0
```

**反向对照必须覆盖两种不同的劣化**（只测一种会漏）：

| 劣化方式 | 实测特征 | 说明 |
|---|---|---|
| **全量重写** | `shared=0 added=5 removed=5` | 每次重新生成所有分块字节 |
| **块边界漂移** | `shared=3 added=0 removed=2` | 内容没变但分块方式变了（例如换了 CDC 参数） |

> 第二种更隐蔽：`added=0` 看起来"很增量"，但 `removed=2` 暴露了旧块被替换。
> **只看 added 会误判为正常。** 所以断言必须同时检查 `added` / `removed` / `shared` 三个量。

**为什么这条可靠**：blob oid 是内容哈希，**只要分块内容不变，oid 就不变**。
这直接观测到了"是否真的只传了增量"，与 git 的打包策略、网络优化无关。

**实现错了会怎样**：
- 每次全量重写 → 所有 oid 变化 → `shared=0`、`removed>0` → **红**
- 误删旧分块 → `removed>0` → **红**

### B3 — append-only 不变量：前缀不变、只增不减

**断言**：B 机追加内容后，A 机拉回时，A 本地文件满足
`oldBytes === newBytes.subarray(0, oldBytes.length)`（旧字节是新字节的**前缀**），
且 `newSize > oldSize`。

**实测依据**：真实活跃会话采样，该不变量恒成立（inode 不变、frame-0 sha 恒定）。

> **限定（重要）**：这是**语义推论 + 本机实测**，不是形式证明。
> append-only 由 DSH 的日志追加语义背书（这比纯统计强），但实测样本仍是有限的。
> 不要把「本机 N/N 通过」当成「永远成立」——**写断言时要标清证据强度**，
> 避免后来人把它当成数学必然去依赖。

**能防住**：整文件重写（会打乱前缀）、乱序写入。

**实现错了会怎样**：任何"先清空再写"的实现 → 前缀被破坏 → **红**。

**注意**：这条不适用于**下行新建**的会话（本地原本没有），
以及 cwd 被重写过的会话（首帧内容变了）。断言要限定在"同一台机器上追加同步"的场景。

## 断言组 C：不污染（防破坏用户仓库）

### C1 — 用户的 ref 全部不变

**断言**：同步前后 `git for-each-ref` 的输出**逐字节相同**
（覆盖 `refs/heads/*`、`refs/tags/*`、`refs/remotes/*`、`refs/stash`）。

**能防住**：误写用户的 branch / tag；误把会话 ref 建到 `refs/heads/` 下。

**实现错了会怎样**：把会话存成普通分支 → 多出 `refs/heads/dsh-sessions` → **红**。

### C2 — 工作区零改动

**断言**：同步前后 `git status --porcelain` 输出相同（含未跟踪文件）。

**能防住**：误 `checkout` 会话 ref 到工作区——这是**最危险的失败模式**，
会覆盖用户未提交的改动。

**实现错了会怎样**：实现里出现 `git checkout refs/dsh-sessions/v1` → 工作区冒出
一堆会话文件 → **红**。

### C3 — 会话 ref 不会被 `git push --all` 顺带推出去

**断言**：在 `git push --all --dry-run` 的输出中，**不出现** `refs/dsh-sessions`。

**能防住**：会话 ref 放在 `refs/heads/` 下（那就会被 `--all` 带上）。

**实测依据**：放在 `refs/dsh-sessions/v1`（不在 heads/tags 下）时，
`git push --all` 不会带它；`--mirror` 也不会。

**实现错了会怎样**：ref 命名空间选错 → `--all` 输出里出现会话 ref → **红**。

### C4 — 默认不产生任何 `~/.dsh` 之外的写入

**断言**：测试全程对**用户真实** `~/.dsh` 做前后 mtime + 内容 hash 快照，断言完全未变。

**能防住**：测试自己污染用户真实数据（这是开发期最该防的事故）。

**注意**：不能要求"`~/.dsh` 整体 hash 不变"——**DSH 运行时它一直在变**
（实测 3 秒内 3 个文件变化，全是正常 append）。
正确的不变量是 **append-only：旧字节仍是新字节的前缀**，而不是"完全不变"。
**这条如果不写清楚，测试会 flaky。**

## 断言组 D：冲突（防静默覆盖）

### D1 — 两端都推进 → 必须 keep-both，且原会话字节级不变

**断言**：
1. 冲突后**原会话目录的字节内容与 mtime 均未改变**（逐字节比对）
2. 远端版本被另存为一个**新的、可寻址的**会话（带来源标注）
3. 返回结果里有可读的冲突报告（不是静默跳过）

**能防住**：静默覆盖本地内容——这是"绝不静默覆盖"原则的直接检验。

**实现错了会怎样**：
- 实现选择"远端赢"并覆盖 → 原会话字节变化 → **红**
- 只保留一份但不报告 → 用户不知道发生了什么 → 断言 3 红

### D2 — 绝不返回 remote-wins

**断言**：对"两端都改同一会话"的输入，`decideConflict()` 的决策**不是** `remote-wins`。

**为什么**：自动合并/覆盖两个走了不同历史的对话流，等于**伪造一段从未发生过的对话**。
对 AI 会话这种内容，比丢数据更危险——用户会以为 AI 真的说过那些话。

**实现错了会怎样**：策略表写错 → 返回 remote-wins → **红**。

### D3 — 同一包重复下行必须幂等

**断言**：同一份远端包连续 pull 两次，第二次**不产生任何写入**，
且结果标记为"已是最新"。

**能防住**：非幂等实现导致重复追加、会话膨胀。

## 断言组 E：可见性闭环（MVP 核心）

> 依据：设计 §11「写盘 ≠ DSH 可见」。
> 外部写入的会话**不会被 DSH 自动收养**，且 `cwd` 不匹配的会话会被主动过滤。
> 所以"文件写完"绝不等于"同步成功"。

### E1 — pull 后会话出现在 workspace 的过滤后成员列表里

**断言**：`entity.sessionIds.includes(sessionId) === true`。

**注意**：只断言"没抛错"是不够的。`attachSession()` 可能**不抛错但被过滤**——
所以必须**回读过滤后的成员列表**再判断。
（实现的 `attachedButInvisible` 检测正是为此，测试要覆盖这条路径。）

**能防住**：cwd 重写错误导致的"静默不可见"——用户看到"同步成功"但侧栏空白。

**实现错了会怎样**：cwd 没重写或重写成非 realpath 形式 → 被过滤 → **红**。

### E2 — cwd 被重写为 B 机的真实仓库路径，且是 realpath 形式

**断言**：B 机落盘文件的 `header.cwd` 满足
`realpath(header.cwd) === realpath(目标仓库路径)`。

**为什么强调 realpath**：`attachSession()` 内部对 `header.cwd` 做
`realpathNormalize()` 后**严格比对**。macOS 上 `/tmp` 会变成 `/private/tmp`，
符号链接、尾部斜杠都会导致比对失败——而失败是**静默**的（不抛错，只是不出现在列表里）。

**能防住**：cwd 重写"看起来对"但 realpath 不等价的隐蔽错误。

**实现错了会怎样**：写入 `/tmp/repo` 而实际路径是 `/private/tmp/repo` → **红**。

### E3 — attach 失败必须回滚本次新建的会话

**断言**：构造 `attachSession` 必败的场景（如 registry stub 抛错）后：
1. 本轮**新建**的会话目录已被**删除**
2. 本轮**追加**的会话**未被删除**，且从备份还原
3. 结果中明确报告失败

**为什么必须区分两者**：
- 新建的会话 → 删除是安全的（操作前它不存在）
- **追加过的会话 → 绝不能删除**，那里面有用户的历史对话

**能防住**：悬空会话（留着但看不见）以及**更严重的误删用户历史**。

**实现错了会怎样**：
- 不回滚 → 悬空会话留在磁盘 → 断言 1 红
- 回滚时把追加的也删了 → **用户历史丢失** → 断言 2 红

### E4 — 目标路径不存在时中止，不写悬空会话

**断言**：B 机未 clone 该仓库时 pull，**不产生任何会话文件**，且返回可操作的错误。

**能防住**：写入指向不存在目录的会话（DSH 打开它会失败或落到错误目录）。

---

### E5 — 下行后可继续对话，且 seq 连续衔接

**断言**：
1. 下行完成后，模拟 DSH 追加一个新事件（`seq = 已同步的最后 seq + 1`）→ 写入成功
2. 追加后文件可正常解码，`nextSeq` 正确递增
3. 该会话的 `header.cwd` **仍是本机路径**（同步过程不得把它改回去）
4. `git -C <cwd> rev-parse --show-toplevel` 指向本机仓库（证明 cwd 语义正确）

**为什么必须有**：「能打开」和「能继续」是两回事。
如果下行的末尾状态不对（nextSeq 错、末尾有半帧），DSH 后续追加会失败或产生 seq 冲突。
**"能打开但不能继续"比"打不开"更糟**——用户以为同步成功了，继续工作时才发现会话坏了。

**实现错了会怎样**：nextSeq 计算错误 → 追加时 seq 冲突 → **红**。

---

## 断言组 F：安全（防恶意/损坏数据）

### F1 — 路径穿越必须拒绝

**断言**：会话 id 为 `../../etc/passwd`、`..`、含 `/` 或 `\` 的载荷，
**必须被拒绝且本机文件系统无变化**。

### F2 — 畸形数据不导致部分写入

**断言**：截断的包、非法 JSON、seq 有缺口的包 → **拒绝且零写入**
（不是"写了前半段再报错"）。

### F3 — 远端内容不可信：不得执行 manifest 里的字符串

**断言**：manifest 中 `worktree` / `branch` 等字段填入命令注入样式
（`$(rm -rf /)`、`;reboot`），同步仍正常完成且不执行任何命令。

**能防住**：把远端数据当指令用。所有 git 调用必须用 `execFile` 传数组，
不能拼 shell 字符串。

## 断言组 G：并发（防与运行中的 DSH 打架）

### G1 — 不写入 LIVE 会话

**断言**：对 `session.lock` 持有 `flock` 的会话发起下行，
**必须拒绝写入**，且会话文件字节不变。

**实测依据**：`session.lock` 上的 flock 是可靠活性信号
（当前对话所在会话探到 LIVE，6 个历史会话探到 IDLE）。

**能防住**：写入活跃会话 → DSH 内存态的 `next-seq` 与磁盘分叉 →
该会话后续写入被拒或产生 seq 冲突。**这是插件不该造成的伤害。**

### G2 — dry-run 也必须报告 LIVE

**断言**：dry-run 模式下对 LIVE 会话调用，**结果中要体现"该会话现在不可写"**，
而不是报告"一切正常"。

**为什么**：dry-run 的承诺是"告诉你实际执行会发生什么"。
如果预演说没问题、实跑却失败，dry-run 就是骗人的。

### G2b — 下行写入的会话必须与 DSH 原生目录结构一致（含 `session.lock`）

**断言**：下行写入后，会话目录内容与真实 DSH 会话目录**结构一致**：
至少包含 `session.v4.jsonl.zstd` 与 `session.lock`。

**为什么这条必须有（它是一条真实存在过的盲区）**：

`isSessionLive()` 的第一步是短路判断：

```js
if (!(await pathExists(lockFile))) {
  return { live: false, checked: true, method: 'no-lock-file' }   // 直接判定"不活跃"
}
```

如果 `writeSession` 创建会话时**不写 `session.lock`**，那么：

1. 该会话的 LIVE 检测**永远返回 not-live**
2. 后续任何下行都会愿意写入它——**即使 DSH 正在使用它**
3. 这正是 §G1 要防的场景，却被"目录结构不一致"整个绕过

**实测依据**（对真实 219 个会话统计 lock 与 log 的 mtime 关系）：

```
sessions with lock              : 219/219
lock mtime 明显晚于 log (>5s)   : 2
lock OLDER than log             : 217/219   ← lock 在会话出生时创建，log 之后持续增长
```

`217/219` 说明 DSH 在**创建会话时**建 lock，而非每次打开补建。
推论：**不写 lock 的会话，DSH 很可能永远不会为它补建**，故该盲区是永久性的。

> ⚠️ 这条是**统计推断**，未拿到 DSH 源码确认「打开会话是否 `O_CREAT`」。
> 断言只管**让我们的产物与原生结构一致**，不依赖那个未确认的结论。

**为什么现有测试全绿却漏了它**：qa 的 G1 用例是在 fixture 里**手工创建** `session.lock`
再测检测逻辑的。而真实下行路径产生的会话**根本没有 lock**——
**测试都在验证"有 lock 时检测对不对"，没人验证"我们产出的会话有没有 lock"。**

---

### G3 — 无 lsof/fuser 时如实报告"没查成"

**断言**：探测工具不可用时，结果标记为 `checked: false`，
**不得伪装成 live:false**。

**能防住**：把"我不知道"说成"没有风险"。

## 断言组 H：锚点提示

> 依据：设计 §6.3 定义了四种锚点状态。锚点**只提示、绝不阻断**。

### H1 — 锚点落后 N 个提交
**断言**：A 在 commit `X` 产生会话 → 上行 → B 的 HEAD 前进 N 个 → 下行，
结果中给出锚点 `X`、当前 `HEAD`、落后数 N（应等于 `git rev-list --count X..HEAD`）。

### H2 — 锚点非祖先（rebase / 强推过）
**断言**：锚点不是当前 HEAD 的祖先时，提示「锚点已不在当前分支历史中」，
**不得**静默按「落后 N 个提交」处理（`rev-list --count` 对非祖先也会给数字，会误导）。

### H3 — 本地缺锚点 commit
**断言**：本地没有该 commit 时提示「请先 fetch」，**不崩溃**。

### H4 — 锚点不阻断
**断言**：锚点严重过时时，会话内容**仍然可同步、可打开**。
这是设计 §6.3「只在 UI 提示，绝不阻断」的直接检验。

---

## 断言组 I：可见性交互（public / consent）

> 依据：设计 ADR-9 与 §9.4.1。实现见 `src/repo-visibility.js`
> （审计时实测 12/12 通过：public→需逐字确认、private→放行、
> 全链路失败→unknown 且仍要求确认、URL 里的凭据被剥离）。

### I1 — public 默认拒绝，逐字确认才放行
**断言**：绑定时 `public` → 不可直接完成；输入错误仓库名 → 不可；输入正确 → 可。
**能防住**：把"public 也能悄悄同步"当成默认行为。

### I2 — private → public 变化必须中止
**断言**：已确认的 public 仓库 → 改私有 → 改回 public → 下一次上行**中止并要求重新确认**。
**能防住**：「今天私有、明天转公开」的静默泄露。
**实现错了会怎样**：只判"当前是不是 public"而不判偏离度 → 该中止的没中止 → **红**。

### I3 — public → public（已确认）必须放行，不重复骚扰
**断言**：用户已逐字确认过 public，后续上行**正常成功**。
**能防住**：每次上行都拦（会让用户干脆关掉插件）。
**注意**：I2 与 I3 是一对**互相制衡**的断言——只写一条都会导致错误方向。

### I4 — unknown 不绑定 consent
**断言**：判定失败（`unknown`）时，用户确认后**下一次上行仍要求确认**
（`unknown` 不作为已确认状态缓存）。

## 断言组 J：备份前置

### J1 — 备份失败则零写入
**断言**：构造备份目录不可写的场景 → 下行**中止**并返回 `backup-failed`，
且本地会话目录**内容 hash 未变**。

**注意**：**不要用 mtime 断言**，但理由要说对。

我最初写的理由是「mtime 精度因文件系统而异，秒级粒度会假绿」——
**这个理由在本项目开发平台（APFS，纳秒精度）上不成立**，
有同事实测 200 次连续写入得到 200 个不同 mtime，mtime 能正确检测到变化。

**真正站得住的两条理由**：

1. **跨平台不可靠**：CI 的 Linux 文件系统、外置卷、网络文件系统确实存在秒级粒度。
   本机是纳秒不代表干净 runner 上也是——而测试的价值在于 **CI 上也稳定**。
2. **语义错配**：`mkdir` 改的是**父目录**的 mtime。当你想判断「这个目录有没有被创建」
   时，mtime 指向的是**错误的对象**。这跟精度无关，是测错了东西。

用**内容 hash + 目录项集合**（`readdir` 前后相同）代替。

> **教训**：说一个不成立的实测理由，比不说更危险——
> 下一个人在 APFS 上一试发现"并不假绿"，就会开始怀疑这份文档的所有结论。
> **理由必须自己验证过，或者明确标注是推理而非实测。**

---

## 断言组 K：机器配置不越界

### K1 — 默认一行都不写
**断言**：绑定仓库、执行同步的**默认路径**中，`~/.ssh/config` 内容的 hash 不变。
**能防住**：主流程偷偷写 ssh config（会与 dsh-remote 的受管块互相锁死，见设计 ADR-8）。

### K2 — 绑定表不含凭据与连接四要素
**断言**：持久化的绑定记录里**不出现** host / user / port / 私钥路径 / 任何密码或 token。
**能防住**：把凭据落盘。

### K3 — 远端 URL 中的凭据被剥离
**断言**：`https://user:token@host/o/r.git` 归一化后，产出中**搜不到** token
（实测：`https://***@host/o/r.git`）。
**能防住**：凭据随 remote URL 进入 manifest / 日志 / UI。

## 附：本项目的断言反模式清单

以下写法在本项目里**已被实测证伪**或**会产生假绿**，禁止使用：

| 反模式 | 为什么错 | 实测证据 |
|---|---|---|
| 用 `zstdDecompressSync(整文件)` 后断言"能解析出 header" | 只解第一帧，静默丢 99.99%，header 是合法 JSON 所以会绿 | 757,118 B → 273 B（真值 3,080,613 B） |
| 断言"远端 git 对象总数增量"来证明增量传输 | git 打包 + 未引用对象不传，导致恒绿 | 连续两次 push，count-objects delta = 0 |
| 断言"文件字节完全相同"来证明会话同步正确 | cwd 重写必然改变字节，字节相同是错的期望 | 见 A1 |
| 断言"`~/.dsh` 前后 hash 完全不变" | DSH 运行时持续 append，必然 flaky | 3 秒内 3 个文件变化 |
| 靠"搜索 zstd 魔数"切帧 | 规范不保证压缩块内不出现该序列；本机 0 假阳性是巧合不是契约 | 257,200 帧中 0 假阳性，仍不可依赖 |
| 断言 `attachSession()` 没抛错就算成功 | 可能不抛错但被 cwd 过滤，静默不可见 | 见 E1 |

## 实现顺序建议

1. **A1/A2/A3**（完整性地基）—— 没有这些，其它断言都建立在沙子上
2. **C1/C2**（不污染）—— 成本极低、价值极高，先上
3. **D1/D2**（不静默覆盖）
4. **E1/E2/E3**（可见性闭环，MVP 的核心价值）
5. **B2/B3**（增量性）—— 需要 git plumbing，成本稍高
6. **G1/G2**（并发）
7. **F1/F2/F3**（安全）—— qa 已有部分覆盖
8. **E5**（能继续对话）—— 与 E1 同批做，它才是"真的可用"的判据
9. **I1–I4**（可见性交互）—— `src/repo-visibility.js` 已实现，可直接驱动
10. **H1–H4**（锚点）、**J1**（备份前置）、**K1–K3**（机器配置）

每组至少要有一条**反向对照**：故意做出错误行为，确认断言会红。
